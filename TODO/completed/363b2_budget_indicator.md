## §1 What was shipped

Per Wf-360-A3 (user directive): the GPU launch dashboard needs a "budget remaining" indicator so operators can see at-a-glance how much of the 10h session cap each launcher consumes, plus the DEFERRED_TEMP wave aggregate from `wave_budget_tracker.py` (per Wf-360-A1 rebalance).

Two surface-level changes:

1. **`molmetal/scripts/gpu_launch_aggregator.py`** (Python aggregator) — emits a new top-level `budget_status` field with:
   - `session_cap_hr` (10.0, per Wf-262 §7.1)
   - `per_launcher` list of `{launcher, budget_hr, remaining_hr, status, status_evidence, wall_projected_hr, pair_progress_share, launcher_status}` entries
   - `total_projected_hr`, `total_remaining_hr` (cross-launcher totals vs session cap)
   - `deferred_temp_total_hr`, `deferred_temp_waves`, `deferred_temp_remaining_hr` (Wf-360-A1 rebalance figure)
   - `honest_framing` (5-line summary with HONEST-NEGATIVE surfacing)
   - New CLI flag: `--budget-summary` emits ONLY the budget_status JSON.
2. **`scripts/gpu_launch_dashboard.sh`** (Bash dashboard) — new `--budget-json` flag emits machine-readable JSON with the same `budget_status` schema (cross-language parity). Existing `--budget-detail` (TSV format) preserved for human consumption.


### §3.1 Status enum

- `WITHIN` — `remaining_hr >= 0` (launcher fits in session cap)
- `OVER` — `remaining_hr < 0` (launcher individually exceeds 10h cap; HONEST-NEGATIVE)

### §3.2 Evidence enum (per-wave, in `deferred_temp_waves`)

- `MEASURED_actual_hr` — `actual_hr` was non-null and > 0 in `wave_budget_report.json`
- `PROJECTED_estimated_hr` — fell back to `estimated_hr` (per-wave PROJECTED)

## §5 Honest framing (party-twenty-spirit §3.5)

### §5.1 MEASURED vs PROJECTED tag discipline

- All `budget_hr` values are **PROJECTED** per Wf-355 (the LAUNCHERS list wall_projected_hr was estimated, not re-measured here).
- DEFERRED_TEMP per-wave `hr` values carry an explicit `evidence` field:
  - `MEASURED_actual_hr` when the wave_budget_report has a non-null `actual_hr`
  - `PROJECTED_estimated_hr` when falling back to `estimated_hr`
- Per-launcher `pair_progress_share` is MEASURED from `pair_progress.ok / total_pairs` (in `gpu_launch_aggregator.aggregate_launcher`).

### §5.2 HONEST-NEGATIVE surfaced

Per `honest_framing` line 5: **2 launchers (wf355_a3 at 12h, g6_recover at 11.4h) individually exceed the 10h session cap and would need cross-session scheduling or a USER_OK waiver.** This is consistent with the Wf-355 wall-projection estimates that have always exceeded the 10h budget — the dashboard now surfaces the overage explicitly rather than silently.

### §5.3 Cross-launcher total is also NEGATIVE

`total_remaining_hr = -43.4h` means the SUM of all per-launcher budgets (53.4h) is 5.34× the 10h session cap. This is expected — the LAUNCHERS list was designed to be scheduler-arbitrated across multiple sessions, not all-at-once within 10h. The `deferred_temp_total_hr = 67.1h` rebalance figure (per Wf-360-A1) further confirms that **the per-session cap is the binding constraint, not the cross-launcher sum**.

### §5.4 Budget discipline preserved

Per Wf-262 §7.1 budget discipline:
- The 10h cap is the **single source of truth** for per-session feasibility.
- Each launcher's `status` (`WITHIN` vs `OVER`) is computed against this cap individually.
- The cross-launcher `total_remaining_hr` is a convenience aggregate, NOT a substitute for per-launcher verification.
- `wave_budget_tracker.py` is the upstream source of DEFERRED_TEMP classifications (via `classify_deferred_class()`); the aggregator's import is lazy + safe (falls back to "DEFERRED_TEMP" default on import failure).
