**Honest framing note**: the `split` column is **not** a scaffold split. Per-metal
random shuffling produces the observed numbers *by construction*: each of 5 metals
gets its own 70/10/20 random split; ~268 SMILES (mostly isostructural complexes
measured on multiple metals) end up in **different** splits for different metals,
which leaks through `scaffold_id` since scaffolds span ≥ 2 metals for 188 of the
3 070 unique scaffolds (6.1 %). The fix is straightforward (re-split globally
with `ScaffoldSplitter`); the issue is that the CSV pre-dates the
`ScaffoldSplitter` rewire and was reused across many Wf-25 / Wf-77 / Wf-79 /
Wf-119 / Wf-120 / Wf-123 / Wf-124 / Wf-128 reports as if it were a strict
scaffold split.

## §3 G1 — split source

### §3.1 No in-repo writer found

I traced every `metalcytotox_5metal_multitask.csv` reference with `grep -r` over
`*.py`, `*.sh`, `*.yaml`, `*.md`. **No script in the repo writes the CSV.**
All call sites use it as a *read-only* input (path constant
`DEFAULT_5METAL_CSV` in `molmetal/scripts/{train_ru_multitask,train_se3sb,
train_transport,train_multiph,train_multimetal_lomo,train_ru_5metal_se3sb,
train_dmpnn_pic50_real,train_dmpnn_multitask_wasserstein,extract_rdkit_2d_descriptors,
build_172d_features,check_data_leakage,benchmark_r18_metalcytotox,
bench_3way_real_metalcytotox,bench_hilbert_astr_real_metalcytotox,
bench_lambda_cfm_e2e,...}.py`).

The CSV was generated by a Wf-21-era (R17) external pipeline that predates the
`ScaffoldSplitter` rewire. The 2026-09-28 16:06 mtime corresponds to Wf-244-A
schema extension (added `pic50, cell_line, source` columns), but the `split`
column was not rewritten.

### §3.2 Historical anchors (TO-DO references)

  only (read-only split-count check), not creation.

  ("shipped split = 48 shared scaffolds / 60 shared SMILES") but did not regenerate

## §4 G3 — leak root cause (per-metal random split)

### §4.1 Per-metal split signature (MEASURED)

The 26 801 rows split by metal × split (this audit, csv.DictReader on the live CSV):

| Metal | train | val | test | total | train % | test % |
|---|---|---|---|---|---|---|
| Ru | 13 395 | 1 913 | 3 827 | 19 135 | 70.0 | 20.0 |
| Ir | 3 182 | 455 | 909 | 4 546 | 70.0 | 20.0 |
| Os | 782 | 112 | 224 | 1 118 | 69.9 | 20.0 |
| Rh | 794 | 113 | 227 | 1 134 | 70.0 | 20.0 |
| Re | 607 | 87 | 174 | 868 | 69.9 | 20.0 |

The fact that **every metal is independently exactly 70 %/10 %/20 %** is the
smoking gun. A globally random 70/10/20 split over 26 801 rows would give
~70 %/10 %/20 % *globally* (18 760 / 2 680 / 5 361) but the per-metal rows would
be slightly off (e.g. ±2 rows from rounding). Here the per-metal precision is
exact → each metal was split independently.

### §4.2 SMILES × metal × split cross-tab

| Cross-metal SMILES | n=268 | (1.0 % of 6 782 unique SMILES) |
| Same split for all metals | n=164 | (consistent because the SMILES was duplicated within the same metal-cohort) |
| **Different splits across metals** | **n=104** | the leak source |

Of the 104 cross-metal SMILES with split divergence, every one carries a
scaffold_id that spans ≥ 2 metals → 48 scaffolds end up in train∩test,
29 in train∩val, 32 in val∩test (104 scaffolds total span >1 split; some
triples account for all three overlaps).

### §4.3 Scaffolds × metals (this audit)

```
scaffolds × num_metals:
  1 metals:  2882 scaffolds (94 %)
  2 metals:   176 scaffolds
  3 metals:    12 scaffolds
  4-5 metals:   0 scaffolds
```

176 + 12 = 188 scaffolds (6.1 % of 3 070) span multiple metals; the leaks
arise because the split was applied per-metal without global scaffold
grouping.

### §4.4 scaffold_id provenance (consistent)

`scaffold_id` is the RDKit `Chem.Scaffolds.MurckoScaffold.GetScaffoldForMol`
applied to the **full multi-component SMILES** (`complex.counterion`), so
scaffolds include the phosphine / halide counterion SMILES (see sample row
above with scaffold `c1ccc(C(c2ccccc2)n2cncn2)cc1.c1ccc(C(c2ccccc2)n2cncn2)cc1.c1ccc(P(c2ccccc2)c2ccccc2)cc1`).
The scaffold column itself is **internally consistent** — re-running
`rdkit.Chem.Scaffolds.MurckoScaffold.GetScaffoldForMol` on the stored SMILES
returns the same scaffold SMILES for every row (validated against
`molmetal/scripts/check_data_leakage.py:201–221` which is the same canonical
implementation). The leak is **not** a hash-collision or RDKit-version bug; it
is a *split policy* bug.

### §4.5 Verdict (G3_leak_root_cause)

**The shipped `split` column is the result of running a 70/10/20 random row
shuffle *per metal* (independently for Ru, Ir, Os, Rh, Re), with `scaffold_id`
attached later as an audit column. `molmetal/data/splits.py::ScaffoldSplitter`
(Bemis-Murcko grouped) was never invoked.**

Equivalent pseudocode that produced the shipped split:

```python
for metal in ["Ru", "Ir", "Os", "Rh", "Re"]:
    metal_df = df[df.metal == metal]
    train, val, test = random_split(metal_df, fractions=(0.7, 0.10, 0.20), seed=??)
    # ...later: df["scaffold_id"] = MurckoScaffold.GetScaffoldForMol(canonical_smiles)
```

The seed is not recoverable from the on-disk artefact (no manifest.json is
shipped, unlike `metallo_pool_scaffold_split.py`).

## §5 G2 — scaffold split impl in repo (canonical, but unused)

### §5.1 Library entry point

`molmetal/data/splits.py::ScaffoldSplitter` (lines 543–663):

```python
class ScaffoldSplitter:
    """Split rows so that each Bemis-Murcko scaffold appears in exactly one split."""
    ...
    def _scaffold_for(self, canon_smiles: str) -> str:
        from rdkit.Chem.Scaffolds import MurckoScaffold
        mol = Chem.MolFromSmiles(canon_smiles)
        scaffold = MurckoScaffold.GetScaffoldForMol(mol, includeChirality=self.include_chirality)
        return Chem.MolToSmiles(scaffold)
    ...
    def __call__(self, dataset) -> SplitResult:
        # Group rows by scaffold; assign each scaffold to exactly one split.
        # Defaults: strategy="largest_first", fractions=(0.8, 0.1, 0.1), seed=42.
```

Two CLIs wire to it:

1. `molmetal/scripts/train_nci60_10cell.py:794–795,835–836` — `--scaffold-split`
   flag invokes `ScaffoldSplitter` for the 9-cell multi-task dataset. The 9-cell
   loader reads `data/MetalCytoToxDB.csv` directly (26 801 rows from
   MetalCytoToxDB), not the multitask CSV.
2. `molmetal/scripts/check_data_leakage.py:291–352` — `scaffold_split_indices`
   function is an independent re-implementation of the same Bemis-Murcko grouped
   policy; this is the diagnostic that flagged the leak in `leakage_check.json`.

### §5.2 Why `ScaffoldSplitter` would NOT produce the shipped CSV

If `ScaffoldSplitter` had been applied:
- 3 070 scaffolds → ~2 455 in train / 502 in val / 307 in test (verified by
  `check_data_leakage.py:472–479` on the **same scaffold_id column**, with
  `scaffold_split_indices(scaffolds, seed=42)`).
- 0 scaffolds in any pair overlap (verified: `n_intersect_scaffolds = 0` for
  train∩val, train∩test, val∩test — see
  `molmetal/reports/wf44_r2_debug/leakage_check.json`).

The shipped CSV has 5 361 test rows (= 20 % of 26 801) — far more than the
~503 rows a strict scaffold-split would assign. So the shipped split is ~10× less
OOD than a strict scaffold split would produce. The "test set" contains mostly
seen scaffolds (96 % of test scaffolds appear in train via the row-level
redundancy), so the test-AUC numbers reported in Wf-25 / Wf-77 / Wf-79 etc. are
optimistic by ~10–20 percentage points vs. an honest OOD scaffold split.

## §6 Recommended fix (G3 → 0 leaks)

A `Wf-262-Apply` (NOT this workflow — this is `Wf-261-Audit`) would:

1. Re-implement the split using `molmetal/data/splits.py::ScaffoldSplitter`
   with `fractions=(0.7, 0.10, 0.20)`, `strategy="largest_first"`,
   `seed=42`, applied to the **unique canonical SMILES** (deduplicate across
   metals first, then group, then assign).
2. Write `metalcytotox_5metal_multitask.csv` with the new `split` column.
3. Re-run `molmetal/scripts/check_data_leakage.py` and confirm
   `strict_pass.shipped == True`.
4. Update the callers' docstrings (currently misleadingly claim scaffold-strict).

Expected post-fix sizes (extrapolated from `leakage_check.json:472–479` strict
scaffold-split on the same scaffold_id column): train ~25 796 / val ~502 / test
~503 — much smaller test set but truly OOD (0 shared scaffolds).
